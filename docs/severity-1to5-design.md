# 严重度体系 1-5 数字分级设计稿

> 状态: 设计讨论稿(2026-08-18) · 目标: 用 1-5 数字刻度替代 error/warn/info 三档语义标签
> 核心原则: **数字不靠 LLM 感觉打分, 靠"两轴事实判断 + 确定性映射"**——LLM 只判事实, 代码映射数字

## 1. 动机

三档标签(error/warn/info)的局限:
- **无阈值能力**: "error"就是 error, 无法表达"必修但非阻塞"与"致命且阻塞"的差别
- **粒度粗**: error 与 warn 之间有大量中间地带(确定性逻辑错 vs 假设性安全后果)
- **不可聚合**: 无法统计"平均严重度""严重度分布"等指标
- **无色彩映射**: 无法用绿→红渐变直观表达

1-5 数字刻度: 可定基线(≥3 必修)、可聚合、可挂色彩(绿→红, 数字越大越严重)。

**风险(必须正视)**: 数字无语义锚点, 若靠 judge "感觉"打分, 3/4 边界会比 error/warn 漂移更大 → 必须锚定在可判定证据上。

## 2. 分级模型: 两轴锚定

**轴1 必然性**(LLM 判断: 是/否):
- `有路径`: 存在真实触发路径(确定性逻辑错误)
- `假设性`: "若 X 失败则…"类故障分支, 无真实必然触发路径
- `纯风格`: 不涉及行为正确性

**轴2 后果**(LLM 判断: 哪一类):
- `致命`: 数据丢失 / 崩溃 / 资金损失 / 严重越权
- `功能错`: 功能错误 / 数据不一致 / 安全风险
- `轻微`: 可恢复的降级 / 防御性缺失
- `无`: 可读性 / 命名 / 风格

## 3. 映射表(确定性, 代码实现)

| 级别 | 语义 | 判定锚点 |
|------|------|---------|
| 1 | 建议 | 纯风格/命名/可读性 |
| 2 | 轻微 | 假设性 + 轻微后果(防御性建议) |
| **3** | **必修(基线)** | **有路径 + 轻微 / 明确约定违反 / 假设性 + 安全后果** |
| 4 | 严重 | 有路径 + 功能错/数据不一致/安全风险 |
| 5 | 致命 | 有路径 + 数据丢失/崩溃/越权 |

设计要点:
- **假设性故障最高 3**(延续 2026-08-15 策略: 不升 4/5)——必修但非阻塞
- **约定违反 = 3**: AGENTS.md 明确约定(如"error 必须处理")违反即必修
- 5 必须同时满足"有路径 + 致命后果", 二者缺一降 4

## 4. 判定流程

```
LLM 审查时对每条 issue 输出:
  "trigger": "real" | "hypothetical" | "style"     ← 事实判断
  "impact": "fatal" | "functional" | "minor" | "none"  ← 事实判断
      ↓
代码映射: 两轴 → 1-5(确定性表, 见上)
      ↓
展示: 数字 + 色彩(1绿→5红) + 语义名(建议/轻微/必修/严重/致命)
```

收益: 同一条 issue 无论跑几次数字不变; judge/质量门/门禁全部消费数字, 不直接依赖 LLM 数字输出。

## 5. 基线制定方法论(三步)

基线是**商业决策**(误报噪音 vs 漏报成本的权衡), 方法:

1. **样本标注**: 收集 dashboard 6 轮修复 + PR #5 历史 issues, 人工标二分类"必须修/可不修"(二分类最容易标, 不纠结数字)
2. **分布校准**: 看两类样本在映射后的分布, 找区分度最大的切分点——基线不是先定的, 是数据告诉你的
3. **golden 验证**: 用现有场景对锚点表做一致性检查(见 §6), 并把 expected 改为"级别区间"断言, 回归守住分级不漂移

## 6. golden 场景校准表(初稿)

| 场景 | 期望级别 | 依据 |
|------|---------|------|
| case-bug(nil panic) | 5 | 有路径+崩溃 |
| case-security(SQL 注入+硬编码) | 4-5 | 有路径+安全 |
| case-severity-security(假设性权限残留) | **3** | 假设性+安全=必修不阻塞 |
| case-convention(约定违反) | 3 | 约定违反=必修 |
| case-bait(性能建议) | 2 | 假设性+性能 |
| case-clean / case-docs | 0 issue | — |

expected.json 改造: `severities: ["warn"]` → `severity_range: [3,3]` 或 `severity_min/max`。

## 7. 门禁线分离(关键)

- **必修线(baseline) = 3**: ≥3 的问题出现在评论中标记"必修", 但**不拦合并**
- **阻塞线(block) = 4**: 存在 ≥4 的 issue → check failure, 拦合并
- 理由: 若必修线即阻塞线, 假设性+安全问题会一直拦合并——回到 8/15 想避免的激进
- 配置: `fail_on_severity: 4`(原 `error` 语义迁移)

## 8. 旧数据迁移

- error → {4,5}, warn → {2,3}, info → 1
- **不能一刀切**: 需逐个复核(部分 warn 是"假设性+安全"应落 3, 部分是"防御性建议"应落 2)
- golden 旧断言全量复核; 历史评论不回溯, 只影响新评审

## 9. judge rubric 同步

- 打分维度"准确性"增加: **严重度与证据是否匹配**(报了 4/5 但 evidence 是"若失败则…" → 扣分)
- judge 输入含映射表, 让其校验"trigger/impact 判断是否合理"而非直接评数字

## 10. 落地步骤

- [ ] P0: prompt 输出 schema 加 `trigger`/`impact` 字段(替换 severity)
- [ ] P0: severity 映射函数 + 1-5 渲染(色彩/语义名)
- [ ] P0: 门禁改 `fail_on_severity: 4`, 评论标"必修"
- [ ] P1: golden 场景标级别区间 + expected 改造 + 回归
- [ ] P1: judge rubric 加严重度匹配校验
- [ ] P2: 历史样本标注校准基线(§5 方法论)

## 附: 与现有体系的关系

- 规则 8(非原则性一律 warn)语义保留: 映射为"假设性 → 最高 3"
- needs_review 标记保留: 不确定设计意图的问题, 级别先给 2-3 + needs_review 标记
- 质量门评分(judge 0-100)是另一层(审查质量), 与 issue 严重度(1-5)正交, 互不影响
