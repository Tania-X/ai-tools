# pr-review 质量打分与自检重写(P1 规划)

> 状态:**已设计,未实现**(方案 2026-08-11 讨论定稿)
> 关联:pr-review 增强 · 对应 CodeRabbit 类产品的"质量评估/自检"能力
> 定位:解决 LLM 审查输出质量不稳定(误报/漏报/幻觉/建议空泛)的兜底机制

---

## 一、背景与动机

pr-review 已具备完整审查链路(整体评论 + 行内线程 + check-run 门禁 + P0 线程交互),
但 LLM 输出质量本质上有波动:

- **误报**:无中生有或过度挑剔的问题(经 v2 改进已下降,但无法根除)
- **漏报**:真正的问题没被审出来,或建议空泛不具可操作性
- **幻觉**:引用了不存在的代码行 / 契约条款

v2 的降误报是从"审查输入"侧(仓库上下文、生成代码排除)改善;**本方案从"审查输出"侧
兜底**——审查完成后引入独立的 judge LLM 打分,不达标自动带反馈重写,仍不达标则明确告知
用户,避免低质量审查悄悄污染 PR。

## 二、方案概览:LLM-as-a-judge 自检循环

```
LLM 审查产出 issues(JSON)
        │
        ▼
Judge LLM 打分(独立 prompt / 独立模型,可选)
  rubric: 准确性 / 可操作性 / 覆盖度 / 噪音
        │
        ▼
score ≥ pass_score ? ──是──▶ 发布评论 + check-run 门禁
        │否
        ▼
重写次数 < max_rewrites ? ──是──▶ 带 judge 的 reasons 整批重审 ──▶ 回到打分
        │否
        ▼
降级提示:不发低质量评论,提醒手动 rerun 或人工 review;
check-run 置 neutral(不阻塞合并)
```

## 三、设计决策

### 3.1 judge 独立于审查者(核心)

用**第二个 LLM(独立 prompt,模型可独立配置)**当质检员,不让审查 LLM 自评——
自评存在"自我感觉良好"偏差。

judge 输入:

1. 审查产出的 issues 清单(JSON)
2. 对应文件 diff(用于核对准确性)
3. 评分标准(rubric)

judge 输出(JSON):

```json
{
  "score": 0-100,
  "verdict": "pass" | "rewrite",
  "reasons": ["逐条说明扣分点(供重写时作为反馈)"]
}
```

### 3.2 打分粒度:整个 PR 审完打一次分

- 不按批次打分:判断"覆盖度 / 噪音"需要全局视角,分批打分成本翻倍且批次间上下文割裂
- 大 PR(多批次)时,judge 输入按需截断(参考 `max_context_chars` 思路,设 `max_judge_input_chars`)

### 3.3 重写策略:带 reasons 整批重审(Reflexion 式)

- judge 的 reasons(如"第 3 条是误报""缺少对 X 的检查""建议不具体")作为反馈注入重写 prompt
- **整批重审而非"只修指出的问题"**:漏报必须重看全部 diff 才能补
- 重写轮次之间的 issues 不叠加,以最后一轮为准

### 3.4 阈值与重试上限

| 参数 | 建议默认 | 说明 |
|------|---------|------|
| `pass_score` | 70 | 低于则触发重写;太低失去门禁意义,太高重试爆炸 |
| `max_rewrites` | 3 | 硬上限,防死循环;每次重写前记录 attempts,达到即降级 |

### 3.5 三次失败降级(用户可见行为)

- **不发布低质量评论**(避免污染 PR 讨论区)
- 发布一条说明性评论,文案示例:

  > ⚠️ 本轮 AI 审查质量评估未达标(3 次重写均低于阈值,最后一次评分 X/100)。
  > 建议:① 稍后手动 rerun 本 workflow;② 或人工 review。

- check-run 置 **neutral**(非 success 也非 failure):"审查质量差"不是代码缺陷,不阻塞合并

## 四、评分维度(rubric)

| 维度 | 考察点 | judge 判断依据 |
|------|--------|----------------|
| 准确性 | issue 是否真对应代码问题(幻觉/误报) | issues 中的行号/引用与 diff 的对应关系 |
| 可操作性 | 修改建议是否具体可执行 | suggestion 是否包含明确的改动方向/代码示意 |
| 覆盖度 | 关键改动是否被审到(漏报) | 新增/删除的核心逻辑是否有对应 issue 或 summary 覆盖 |
| 噪音 | 是否过度挑剔无关紧要的 | warn/info 级问题是否聚焦于真实风险 |

### 4.1 低成本校验层(judge 的辅助输入)

> 思路:质量打分不必全交给 LLM——**确定性内容用确定性工具**,LLM 只判断语义问题。

**两层校验,成本递增:**

| 层 | 内容 | 成本 | 说明 |
|----|------|------|------|
| 结构校验 | JSON schema、行号 ∈ diff 新增行、severity 合法、file 存在 | 零(纯代码) | pr-review 已有部分,固化进 judge 前置校验 |
| linter 交叉验证 | 对 PR 涉及文件跑对应语言 linter,产出确定性错误清单,作为 judge 输入之一 | 低(秒级,无 token) | 见下 |

**linter 结果的三种用法(作为信号,不直接否决):**

1. LLM issue **命中** linter 也报的错误 → 高置信,加分
2. LLM issue 是 linter **未报**的语义级问题 → 保持 LLM 判断(linter 只覆盖语法/局部规则,不覆盖语义,不因"linter 没报"就否决)
3. LLM issue 与 linter 冲突(如行号根本不存在)→ 疑似幻觉,扣分

**关键原则:linter 结果只作 judge 的参考信号,不直接否决 LLM 输出**——否则 LLM 变成 linter 的复读机,且 linter 自身误报会反向污染审查结果。

**配置草案(quality_gate 下):**

```yaml
quality_gate:
  ...
  lint:
    enabled: true            # 关闭则完全跳过本层
    only: [py, js, go]       # 只对已接入的语言跑,其他语言跳过
    # 语言 → 命令由实现侧维护;linter 版本需锁定(pin),避免输出格式漂移
```

## 五、成本分析

最坏情况 = 1 次原审 + 3 次重写 + 4 次 judge ≈ **4 倍审查成本**。

- judge 输入 = 审查输出 + diff 摘要,远小于审查本身的输入,单次成本占比低
- DeepSeek/Kimi 价格下,单 PR 全量审约几分钱,4 倍仍在可接受范围
- 保留 `quality_gate.enabled` 开关,异常时可一键关闭

## 六、与现有代码的接缝(实现时参考,侵入性小)

改动集中在两处:

1. `ReviewRunner.run()` 末尾:result 产出后先过 judge;不通过则带 reasons 重跑 `_review_batch`(整批),重复至 `max_rewrites`
2. `main.py` 发布前:根据最终 verdict 分流——通过走正常发布;降级走说明评论 + neutral check-run

新增模块建议:`pr-review/pr_review/quality.py`(Judge 评分 + 重写循环 + rubric prompt)

## 七、配置项草案(.ai-review.yaml)

```yaml
quality_gate:
  enabled: true        # 一键开关
  judge_provider: deepseek   # 可选,默认同审查 provider
  judge_model: deepseek-chat # judge 用模型(可独立于审查模型)
  pass_score: 70       # 低于则触发重写
  max_rewrites: 3      # 重写硬上限
  max_judge_input_chars: 8000  # judge 输入预算,大 PR 截断用
  judge_max_tokens: 1200       # judge 输出预算; 太小会把 JSON 截断 → 评分整轮作废(§9.6)
```

## 九、可验证性、判官故障与职责边界(P0-1 / P0-3 / P0-4 / P0-5)

> 来源: [误报现场报告](pr-review-false-positive-field-report.md)。报告统计了 15 轮门禁级判定中
> 8 条误报/设计意图/重复(约 53%),其中 6 条属"无法给出可反驳证据"的断言(A/B/F 类),
> 2 轮整体判断因 judge 输出无法解析而不可用(E 类)。本节是这两项的实现口径。

### 9.1 P0-1 可验证性字段(确定性规则,零 token)

issue schema 新增 `verification`(可验证路径),prompt 规则 18 要求门禁级问题必须填,三选一:

| 写法 | 含义 |
|------|------|
| 复现输入/命令 | 如 `POST /api/x 传 tenant_id=abc 返回 500` |
| 与之矛盾的现有测试名 | 需说明该测试为何挡不住 |
| `none: 属推演` | **模型自认**拿不出验证路径(逃生口: 宁可自认,也不要编造) |

`quality.per_issue_verify` 的确定性处理(逐条,不整批重写):

| 条件 | 动作 | 理由 |
|------|------|------|
| 级别 ≥4 + `verification` 自认推演 | **降级到 2**(轻微) | 映射表里"无路径"就该是轻微级;自认无法证明的断言不该拦合并 |
| 级别 ≥4 + 无 `verification` **且**无 `evidence` | **降级到 3**(必修不阻塞) | 无任何事实支点;与"自认推演"分档,保留必修可见性 |
| 级别 ≥4 + 无 `verification` 但有 `evidence` | **不降级**,只出结构信号 | `evidence` 本身可能就是验证路径,仅凭字段缺失降级会误伤真问题 |
| 级别 ≥3 + 无 `evidence` | 只出结构信号,不降级 | 3 级本就不阻塞;降 3→2 会白丢"必修"标记 |

分界要点: **"字段缺失"与"无依据"不是一回事**。只按新字段缺失降级,会让不认新字段的模型
把所有门禁级问题一起降级——那是比误报更糟的信号丢失。

### 9.2 P0-3 判官故障留档(E 类)

故障形态: judge 输出了可读文字但无法解析成 JSON(线上 2/15 轮)。原实现把它当成
"0 分 + 判负",于是触发 3 次重写(每轮照样解析不出),最后整轮降级、审查被扣下不发——
**工具故障伪装成了审查质量差**。

现在的口径:

1. `JudgeResult.parse_failed` 区分"故障"与"判负"(判负仍是真实低分)
2. 解析失败先按"只输出 JSON"的严格指令**重试一次**(线上failure 多为前后带解释文字),仍失败才判故障
3. 判故障 → `quality_verdict="judge_error"`、`quality_score=None`(**不给 0 分**,0 分会读成"质量差")、**不重写**(故障在工具侧,换轮次无用)
4. 审查照常发布(issues 是产品),评论顶部标"质量评分不可用(工具故障, 非审查判负)",judge 原文进 `<details>` 折叠块留档
5. **评分与门禁解耦**: check-run 结论仍由 issue 级别决定 —— 否则一次 judge 抖动就能改掉合并门禁,门禁含义随工具状态漂移

### 9.3 P0-4 技术栈声明 + 语言语义边界(2026-09-13)

**治的病**: §3.1 的 8 个实例同属一类——「**正确的 Python 代码 + 与 Java/JS 直觉相反的语言规则**」。
评审被问"这条语言语义对不对"时没有事实来源, 只能拿先验猜。换更强的模型不会让它消失。

**三部分**:

1. **声明技术栈**(`.ai-review.yaml`)

   ```yaml
   stack:
     languages: [python]
     framework: fastapi
     async_runtime: anyio
     notes:
       - "领域错误由 interfaces/api/errors.py 集中注册 handler, 路由内不捕获"
   ```

2. **注入语言语义清单 + 规则 19**: `prompt.LANGUAGE_SEMANTICS["python"]` 那 6 条逐条对应
   §3.1 的实例(真值判断看容器非空 / 异常按类集中注册沿 MRO 匹配 / async 生命周期 /
   dataclass 不校验 / 动态类型无编译期检查 / `x or default` 与 `default_factory`)。
   规则 19 要求: 主张"违反语言语义"的问题必须在 `verification` 里引用规则或给可复现片段
   (如 `python -c "print(bool({'a': []}))"`), 凭其它语言的直觉不算依据。

3. **golden 用例 `case-semantics-*`**(报告 P0-4 第 3 条): 代码正确但极易被跨语言直觉误报的样本,
   期望门禁级 findings = 0; 指标"语言先验误报 ≤1"(现状 8/15 轮)。

> 注入位置: 动态事实(**含技术栈与 CI 结论**)进 user message 的
> `## 技术栈与语言语义边界` 块, 不进 system 常量——同一份 system prompt 要服务所有仓库。

### 9.4 P0-5 职责边界: 先问"该由谁负责", 再决定报不报(2026-09-13)

**总纲**(用户提出, 覆盖全部误报类别):

```text
编译器/类型检查器能确定的 → mypy / ruff        (确定、便宜、可复现)
运行时行为               → pytest              (测试的职责)
语义 / 设计取舍           → 人                 (设计意图)
AI 评审                  → 只负责以上三类【之外】的部分
```

15 轮实测的误报几乎全部落在前三类里: "这个类型/框架语义对不对"(工具职责)、"这段代码运行时
会不会走那条分支"(测试职责)、"这个设计是否有意为之"(人的职责)。评审被迫回答前三者的问题时,
只能靠语言先验去猜——§3.1 的 8 个实例就是这么来的。

**机械化实现(四步, 本 PR 落地前三步)**:

1. 仓库声明工具链与其负责的维度:

   ```yaml
   toolchain:
     enabled: true
     checks:
       - {name: "Lint (ruff)",        dimension: style,  tool: ruff}
       - {name: "Type check (mypy)",  dimension: typing, tool: mypy}
       - {name: "Test (pytest)",      dimension: test,   tool: pytest}
   ```

2. **只信真实结论**: 审查时按 `name` 匹配该 commit 的 CI check-run, **只有结论为
   success/neutral/skipped 的才算"已由机器确认"**; 拿不到 CI 结论就不注入(未知 ≠ 已确认)。
   匹配不到、API 失败、工具链未声明 → 一律按"未知"处理, 审查照常进行。

3. **确定性规则(P0-5)**: issue 落在"已确认维度"上(`type_consistency→typing`,
   `convention/style→style`)且 `tool_gap` 字段为空 → 降级到 **2**, 并给 judge 出结构信号。
   填了 `tool_gap`(说明该工具为什么没拦住: 文件不在检查范围 / check 未配置或改名 / 规则未覆盖)
   则保留原级。

   **为什么用字段而不是关键词匹配**(三轮评审的教学案例):
   一开始从 detail/evidence 的自由文本里猜"有没有解释", 结果连续被打穿三次——
   ① 裸 `"检查范围"` 是 `"在检查范围内"` 的子串, 相反语义也命中;
   ② 改成"文本里出现工具名就算", `"mypy 本应抓到却没有"` 又命中;
   ③ 补 `"缺失"/"改名"` 等否定词, 结果 `"参数类型标注缺失"` 这类无关描述也命中, 规则大面积空转。
   结论: **从自由文本里猜语义这条路走不通**, 与 P0-1 同样改成"让模型显式填字段",
   确定性层只判字段是否为空。

4. (未做) golden `case-toolchain-covered`: diff 里放一个 mypy 能抓的类型错误 + 声明仓库有 mypy
   → 审查应**不报**(CI 会红), 真要报也必须附"为什么 mypy 漏了"。

**约定违反的档位(2026-09-13 拍板"按 P0-5 来")**: `category=convention` → **建议档 2**,
在任何 severity 上一律不计门禁。原先的策略锚点"明确约定违反 = 3(必修不阻塞)"**已废止**,
`docs/severity-1to5-design.md` 同步更新。实现是独立规则(4a), 与"高判分档链"解耦:
约定档位不因假设性措辞、自认推演等信号而改变, 也不依赖 severity 是否 ≥4。

> 理由(职责边界): 约定违反该由 ruff 与仓库约定文档负责; 评审报它属重复劳动,
> 且"违反约定"与"会造成故障"是两件事——让约定类问题长期占据必修线, 是门禁噪音的来源。

### 9.5 与已有机制的关系

- 与 §3.5 的 `degraded`(重写耗尽仍不达标)是**两种不同状态**: `degraded` = 判负(有过有效评分), `judge_error` = 不可知(从未拿到有效评分)
- 与逐条验证层(§4.1 思路)同一条线: 能用确定性代码判的,不进 LLM

### 9.6 判官输出被 max_tokens 截断(2026-09-18)

**治的病**: §9.2 只解决了"故障怎么呈现",没解决"故障为什么会发生"。
judge 的输出预算被硬编码为 `max_tokens=400`,而 rubric 有 6 个维度、还要求"逐条说明扣分点":
中文一条理由约 200 字(≈120-200 token),**3 条就超预算** → JSON 在第三条理由中间断掉 →
缺收尾 → 严格解析失败。重试更没救: 它沿用同一个 `kwargs`,预算一样,装不下就是装不下。
结果连续两轮失败,评分作废(openrag-lab PR #16 现场: 两次归档输出都断在第三条理由中间)。

**四个改动**:

1. **预算可配且给够**: `quality_gate.judge_max_tokens`(默认 1200)。参照 `review_max_tokens` —— 本仓
   早就判定"gateway 默认 1024 对审查输出太小",没理由给 judge 的预算比审查本体还紧。
   调大上限**不增加成本**: 输出 token 只在真写出来时才计费。
2. **区分成因**: gateway 此前把 `choices[0].finish_reason` 丢掉了,而它是"被截断"(`length`)与
   "格式跑偏"(`stop`)的唯一判据。现在 `ChatResponse.finish_reason` 一路带到 `JudgeResult`,
   重试策略据此分叉:
   - `length` → **加预算**(×2,下限 +800)**+ 要求更短的输出**(最多 2 条, 每条 ≤60 字)
   - 其他 → 沿用"只输出 JSON"的严格指令, 预算不动(格式问题加预算治不了)
3. **留档不再截在故障点上**: 故障原文留档上限 500 → 2000 字。旧上限让归档的两次输出**都恰好 500 字**,
   连"模型到底写完没有"都看不出来 —— 排查时只能靠猜,这才是事故拖了两轮才定位的原因。
   两次尝试的抢救理由也合并保留(首次那份是未被干预的原始形态)。
4. **prompt 侧同步限长**: 明确"reasons 最多 3 条, 每条 ≤80 字, 不要复述 rubric / 不贴代码",
   从源头把输出压在预算内,而不是靠事后截断。

**评论上的可见变化**: 判官故障时若成因是截断, 评论会写明"输出被 `max_tokens` 截断, 可调
`quality_gate.judge_max_tokens`"—— 故障从"玄学"变成"一个可调旋钮"。
